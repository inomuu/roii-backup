### เหตุผลที่ D1 เป็นแกน

Steam Market จับคู่ของด้วย `market_hash_name` — **ชื่อเดียวกัน = สินค้าเดียวกันทุกชิ้น** ตลาดโชว์เป็น
order book เดียวต่อชื่อ และ **ค้นหา/ตั้งราคาตาม stat ไม่ได้** ⇒ ของที่ roll มาต่างกันแต่ชื่อเดียวกัน
จะกลายเป็น lemon market: ทุกคนลงชิ้นที่แย่ที่สุดที่ราคาต่ำสุด คนซื้อแยกไม่ออก
(CS2 อยู่ได้เพราะมี inspect + เว็บนอกทั้งระบบนิเวศ เกม idle ไม่มี)

นี่คือเหตุผลที่ของ TBH เป็น **ชนิด × grade × level** เฉย ๆ และเป็นเหตุผลที่เขา **ห้าม list ของที่ใส่ crystal
แล้ว** — ของที่ไม่ fungible ต้องออกจากตลาดนั้น

## 2. โมเดลใหม่ — สี่สถานะของชิ้นหนึ่ง

```
ดรอป            →  BASE (fungible)        ชนิด × tier, stat ตายตัว, ไม่มี ★/line
                   เก็บเป็น "count" ใน ledger  ไม่กินช่องกระเป๋า  ขายได้ทุกตลาด
   │
   ├─ ผสม 6 ชิ้น  →  BASE tier สูงขึ้น + Gil + material     (auto ที่ tier ต้น)
   ├─ ย่อย         →  material + Gil                        (tier สูงเท่านั้น)
   └─ ถอนออกมาใส่  →  INSTANCE                              กินช่อง, ใส่ได้, ยังขายได้
          │
          └─ enchant/crystal/card  →  INSTANCE ที่ทำเพิ่มแล้ว = **bound ถาวร** ขายไม่ได้
```

- **ความลึกทั้งหมดย้ายไปอยู่หลังการลงมือของผู้เล่น** — ★/line/crystal/card เป็น *ผลของสิ่งที่ผู้เล่นทำ*
  ไม่ใช่ของขวัญจากการดรอป
- **ของดิบเป็นสินค้า, ของที่ทำเพิ่มแล้วเป็นของส่วนตัว** — เส้นเดียวกับ TBH แต่บังคับแข็งกว่า
  (เขาให้ถอด crystal ออกเพื่อ list ได้, เรา bound ถาวร → ไม่มีช่องล้างของกลับเป็น fungible)

## 2.5 ช่องอุปกรณ์ + main stat ต่อช่อง (2026-09-14)

เทียบกับ TBH (`taskbar-hero-item-study.md` §1.6 + ตารางต่อช่องที่ไล่มาจริง) แล้วตัดสินใหม่ทั้งชุด
เพราะชื่อช่องเดิมของเรา **ทำให้เข้าใจผิด**: `HeadMid` แสดงเป็น "Face" (หน้ากาก) และ `HeadLow`
แสดงเป็น "Aura" (ออร่า) — สามช่อง "หัว" ที่ไม่เกี่ยวกับหัวสองช่อง

### กฎที่ยืมมาจาก TBH (มีหลักฐานต่อช่อง ไม่ใช่เดา)

1. **หนึ่งช่อง = หนึ่งแกน** — อาวุธให้ ATK ดิบ · เกราะให้ DEF ดิบ · มือรองให้แกน "สไตล์" ·
   **accessory ไม่มี main stat เลย** (Diamond Ring มีแต่บรรทัด bonus และไม่มี grade Common)
2. **แกนดิบไต่ ×11 ทั้งบันได · แกน % ไต่แค่ ×2-4** (Block ×4.0 · ASPD ×2.3 · Max HP ×2.2 vs ATK ×10.8 · Armor ×10.9)
   — เพราะ % ที่ ×11 จะทะลุเพดาน (block 100%, ASPD ชน tick) ⇒ **อย่าใช้ตัวคูณ grade เดียวกับทุกแกน**
3. **งบหั่นตามช่องด้วยสัดส่วนคงที่** (TBH: หมวก = 0.5 ของเกราะตัว ทุก grade) ไม่ใช่ author ต่อ def

## 3. ผสม (Fusion) — กฎสุดท้าย

| เรื่อง | กติกา |
|---|---|
| input | **6 ชิ้น GRADE เดียวกัน — ชนิด / หมวด / tier อะไรก็ได้** (D6) |
| output grade | **grade +1** (สำเร็จ) |
| output ชนิด | **สุ่ม** (D7) |
| output tier | **เฉลี่ย tier ของ input ปัดด้วย RNG: `P(ขึ้น) = เศษ`** (D13) |
| จ่ายเพิ่ม | **Gil + material** ทุกครั้ง ทั้งสำเร็จและ fail (D3, D5) |
| อัตราสำเร็จ | s1→s5 100% · s5→s6 75% · s6→s7 50% ⚠️ PROVISIONAL |
| fail | ของ 6 ชิ้นหาย ได้ **Gil + material น้อยกว่าย่อย** ไม่คืนของ (D5) |
| auto-combine | เปิด default เฉพาะช่วงที่สำเร็จ 100% **หยุดตรงที่ fail เริ่ม** |
| เพดาน | **grade สูงสุดที่ผสมได้ = เพดานของแพตช์นั้น** (launch = Beyond) |

### ทำไม input เสรี + output สุ่ม = ได้ทั้งความง่ายและอุปสงค์

input เสรีคือกฎที่จำง่ายที่สุด ("6 ชิ้น tier เดียวกัน จบ") — ไม่ต้องจำว่าอะไรผสมกับอะไรได้
แต่ถ้า **output เลือกได้ด้วย** ผู้เล่นจะพึ่งตัวเองได้ 100% ⇒ ไม่มีใครต้องซื้ออะไรจากใคร ⇒ ตลาดเงียบ

**output สุ่มคือที่ที่อุปสงค์เกิด**: อยากได้อาวุธ Beyond แต่ผสมได้หมวก Beyond ⇒ ต้องไปแลก/ขาย
TBH ทำตรงข้ามกับเราครึ่งหนึ่ง (จำกัด input 3 category แต่สุ่ม output) — **เราเสรี input แล้วสุ่ม output
ซึ่งง่ายกว่าเขาอีกขั้นแต่ยังรักษาเหตุผลของตลาดไว้**

### tier ของผลลัพธ์ — เฉลี่ยแล้วปัดด้วย RNG (D13)

```
tier_out = floor(avg)  โดยมีโอกาส = เศษ ที่จะเป็น floor(avg)+1
เศษ = 0 → อยู่ tier เดิม (ไม่ปัด)
```

| ใส่ | avg | ผล |
|---|---|---|
| s1×6 | 1.00 | s1 แน่นอน |
| s1×3 + s5×2 + s7 | 3.33 | s3 67% / **s4 33%** |
| s7×4 + s6×2 | 6.67 | s6 33% / **s7 67%** |
| s7×5 + s6 | 6.83 | s6 17% / **s7 83%** |
| **s7×5 + s1** | **6.00** | **s6 แน่นอน** — ขยะ 1 ชิ้นดึงลง 1 ขั้น ไม่มีลุ้น |
| s7×6 | 7.00 | s7 (เศษ 0 → ไม่ปัดขึ้นเป็น s8) |

**คุณสมบัติที่พิสูจน์แล้ว** (ไล่ครบ 117,649 คอมบิเนชัน):
1. **ไม่มีทางได้ tier เกินที่ใส่ไป** — `ceil(avg) ≤ max(input)` เสมอ ⇒ ฟอก tier ไม่ได้
2. **ไม่เอนเอียง** — ค่าคาดหวัง = ค่าเฉลี่ยจริงพอดี (4.000 จากการไล่ทุกเคส) ต่างจากปัดลงล้วนที่เสียมูลค่า 11.5%
3. **ทิศถูก** — ยิ่งใส่ของ tier สูง โอกาสได้ tier สูงยิ่งมาก
4. **ไม่มีกรณีพิเศษ** — เศษ 0 ให้ P(ขึ้น) = 0 เอง (ถ้าใช้ `P(ขึ้น) = 1−เศษ` จะได้ s4 จาก s3×6 = สร้าง tier ที่ไม่มีใน input)

## 3.6 ตลาด: Gil AH พัก → ลำดับการเปิด grade ผูกกับตลาด (D10)

**Gil AH พักไว้** — เหตุผล: ซ้อนสองตลาดทำให้ของชิ้นเดียวมีสองราคา (เกิด arbitrage + ผู้เล่นต้องเรียนสองระบบ)
และผู้เล่นแนวนี้ต้องการเงินจริงมากกว่าเงินในเกม (TBH ยืนยัน: loop หมุนรอบ Steam Market, gold เป็นแค่ค่าทำของ)

- โค้ดที่มีอยู่ **ไม่ทิ้ง**: `commodity.rs` (order book + invariant harness, 2,178 บรรทัด) + `market_access.rs`
  → **dormant ปลุกได้** เทสยังรันในชุด 242 ของ verify-server
- **Gil เปลี่ยนบทบาท**: จากสื่อแลกเปลี่ยน → **ค่าทำของล้วน** (ผสม / ย่อย / คราฟ / enchant)
  ⚠️ ปุ่มเดียวที่คุมมูลค่า Gil จึงเป็น**ค่าทำของ** — ต้องดูดให้พอ ([[monetary-policy]]: faucet 24/7, sink ต้องโตตาม)
- crowd-scaled drop (∝1/N) + mint quota = กลไกของตลาดเงินจริง ⇒ **พักตามไปด้วย** ที่ launch ใช้อัตราคงที่

**กฎลำดับที่ล็อกไว้**: **grade 8+ (Celestial/Divine/Cosmic) ไม่เปิดก่อนตลาดเปิด**
เพราะเวลาต่อชิ้น 92 วัน / 552 วัน / 9 ปี มีเหตุผลในฐานะ**สินทรัพย์ที่ซื้อขาย** ไม่ใช่เป้าฟาร์ม
— เปิดตอนไม่มีตลาดคือสร้างกำแพง (อาการที่ผู้เล่น TBH บ่นเรื่อง Divine/Cosmic มาจากตรงนี้)
⇒ **launch = Beyond (solo chase 4-5 ปี ไม่ต้องมีตลาด)** → Steam market เปิด → แล้วค่อยเปิด grade 8-10

⚠️ ต้องเคาะ: **Steam market ยังเป็น 2nd launch อยู่ไหม** — มันกลายเป็นตลาดเดียวของเกมแล้ว

## 3.7 Mint Coupon — คันบังคับตลาด + track ถาวร (จาก WoG, user 2026-09-14)

```
coupon: 1 ใบ / 4 ชม. · เก็บได้สูงสุด 5 ใบ (= 20 ชม.) · ซื้อขายไม่ได้ แจกเป็นเงินไม่ได้

ปลายทาง B — stat ถาวร ฝั่งรับเท่านั้น: ขั้น N ใช้ N ใบ
```

### ทำไม throttle ชนะ gate (ตัวเลข)

| | คนเล่นปกติ | บอท |
|---|---|---|
**Gate** (Cube Lv10 / resale lock / ห้ามขาย grade ต่ำ) | **เจ็บทุกคนเท่ากัน** ตั้งแต่วันแรก | ฟาร์มผ่านครั้งเดียวจบ |

และ replay-verify กันของปลอมไปแล้ว ⇒ ภัยที่เหลือคือ "ปริมาณการฟาร์มที่ถูกกฎ" ซึ่ง throttle ตอบตรงจุด

### ผลพลอยได้ 2 ข้อที่สำคัญกว่าการกันบอท

1. **coupon สร้างอุปสงค์ให้ระบบผสมเอง** — ผู้เล่นได้ของ ~84 ชิ้น/วัน แต่ mint ได้ 6 ⇒ **92% ต้องเข้าเตาผสม**
   และตลาดจะมีแต่ของที่ "คิดแล้วว่าคุ้มกับ 1 coupon" ⇒ ไม่ล้นตลาด ราคาไม่พัง
2. **ตลาดได้ราคาพื้นที่คิดเป็นพลังถาวร** — ทุกครั้งที่เลือก mint คือการสละ stat ถาวร ⇒ ไม่มีใครขายถูกกว่ามูลค่า
   ของ stat ที่เสียไป ⇒ **อุปทานทั้งเซิฟ = ปริมาณพลังถาวรที่ผู้เล่นยอมสละในวันนั้น**
   (คันคุมอุปทานที่อธิบายง่ายกว่ากฎห้ามขายทุกแบบที่ TBH ต้องใส่หลังวิกฤต)

### ⚠️ track ถาวรต้องแบกแต่ stat ที่ "เฟ้อแล้วไม่พัง" (user สังเกตจาก WoG: max HP เฟ้อไปก็ไม่มีผลมาก)

| ใส่ได้ | เพราะ |
|---|---|
| **Max HP** | เพิ่มความอึด **ไม่แตะจังหวะฆ่ามอนเลย** |
| **DEF** | สูตรเรา `dmg × K/(DEF+K)` โดย **K = 500 + 50×เลเวลผู้โจมตี** ⇒ diminishing ในตัว + K โตตามคอนเทนต์ ⇒ ตันเอง |
| **HP regen / heal%** | ผลจำกัดด้วยดาเมจที่เข้ามาต่อวินาที |

| ห้ามใส่ | เพราะ |
|---|---|
| **ATK** | เชิงเส้นกับดาเมจ ⇒ บีบเวลาฆ่า ⇒ **พัง band pacing ที่จูนไว้ทั้งหมด** |
| **Crit / Crit DMG / ASPD / Dodge** | ตัวคูณบนดาเมจ หรือชนเพดาน (crit 100% · ASPD +200% · dodge ทำให้คอนเทนต์ไร้ความหมาย) |
| resist / DR | ปลอดภัยแต่ **ตันที่ 75% / 50%** ⇒ ใบต่อไปไร้ค่า ผู้เล่นรู้สึกถูกหลอก |

⇒ **เลือกแต่ฝั่งรับ ⇒ faucet 6 ใบ/วันวิ่งได้ตลอดกาลโดยไม่พังบาลานซ์** และ "เลือก mint แทนอัพ stat"
= จ่ายด้วยความอึด ไม่ใช่ดาเมจ ⇒ จังหวะฆ่ามอนที่จูนไว้ไม่ขยับเลย

### ตัวหน่วง: ขั้น N ใช้ N ใบ

6 ใบ/วัน = 2,190 ใบ/ปี ⇒ ถ้าใบละ +0.5% คงที่ = **+1,095%/ปี = ระเบิด**
`ขั้น N ใช้ N ใบ` ⇒ หนึ่งปีได้ **~ขั้น 66** ⇒ ถ้าขั้นละ +1% = **+66%/ปี** (≈ 2 grade) ⇒ พอดี

### ยังไม่เคาะ
- **stat ถาวรลงที่บัญชีหรือต่อตัวละคร** (account-wide ง่ายกว่าและปลอดภัยกว่า)
- **ซ้อนกับ Apex ไหม** — Apex ก็เป็นแต้มสเตตัสถาวร ⇒ ทางสะอาดคือ coupon → แต้ม Apex (ใช้ UI/กฎที่มีอยู่)
  แต่ต้องปลด Apex ให้ใช้ได้ตั้งแต่ต้นเกม ไม่ใช่หลัง cap
- **pass แจก coupon ได้ไหม** — ตามกฎ "ซื้อขายไม่ได้" ควรไม่ได้ (หรือได้แบบจำนวนคงที่ ไม่ scale ตามเงิน)
  เพราะปลายทางเป็น stat ถาวร ⇒ ขาย coupon = ขาย power ตรง ๆ

## 7.6 ข้อผูกมัดฝั่ง Steam (ยังไม่สร้าง generator — แต่ตัดสินแล้ว 2026-09-15)

Steam Community Market จับคู่ประกาศขายด้วย `market_hash_name` ของ **itemdef** — property ที่ติดกับ
ชิ้น (เช่น grade) ตลาดมองไม่เห็น ⇒ **ทุก (ชนิด × tier × grade) ที่ขายได้ต้องเป็น itemdef ของตัวเอง**
(≈1,939 entry ที่ launch) นี่คือข้อบังคับของแพลตฟอร์ม ไม่ใช่ทางเลือก

สิ่งที่ตัดสินแล้ว:
1. `ItemDef.num` — เลขถาวรต่อไอเทม assign แล้ว 1..398 (0.0.376) **append-only ห้ามใช้ซ้ำ ห้ามขยับ**
   → `itemdefid = num × 16 + grade_step` (16 = เผื่อบันไดโตเกิน 10)
2. `market_hash_name` derive จาก `Item::product_key()` (`sword_s7#Beyond`) — **ไม่ใช่**จากชื่อที่แปล
   ชื่อบนจอเปลี่ยนได้ทุกวัน hash name เปลี่ยนไม่ได้เลย
3. ไฟล์ `data/steam_itemdefs.json` = generate จาก catalog + commit + เทส append-only (แถวเดิมห้ามเปลี่ยน)
   เป็นชั้นที่ 4 ของโมเดลข้อมูล (ดู §7.7) และเป็นชั้นเดียวที่**คนนอกถือสำเนา** (Valve)
4. ของที่ enchant/ใส่การ์ดแล้ว = bound ⇒ ไม่มีวัน mint ⇒ เซ็ต itemdef = (ชนิด × tier × grade) พอดี ไม่บานปลาย
5. server เป็นคนเดียวที่ mint (ถือ publisher key) — client อ่านคลังผ่าน Steamworks เท่านั้น

## 7.7 โมเดลข้อมูล 4 ชั้น + แผนที่การจูน (2026-09-15)

```
1. SOURCE   data/game_data.json (คนแก้) — items ฐาน · monsters · zones · loot_rules · gear_overrides
            ยาม: CONTENT_DIGEST · catalog_hygiene (สำเนา StreamingAssets/godot ต้องตรง, num ไม่ซ้ำ/ไม่ขยับ)
2. DERIVED  โค้ด รันตอนอ่าน — grade ×1.30/×1.15 · authored_lines · fusion · product_key
            ยาม: sim_core::VERSION + version gate + goldens
3. BAKED    ตอน build โซน → อยู่ในเซฟ — drop table / grade odds / override rows ต่อมอน
            ยาม: golden hash (bless ครั้งเดียวต่อการเปลี่ยน)
4. GENERATED commit + เทสไม่เก่า — เฉพาะ registry ภายนอก (steam_itemdefs.json, §7.6)
```

กฎว่าของใหม่อยู่ชั้นไหน: **อยากแก้โดยไม่ build client → ชั้น 1 · กำหนดรูปร่างระบบ → ชั้น 2 ·
ต้องนิ่งข้ามเวอร์ชันเพราะคนนอกถือ → ชั้น 4**

`gear_overrides` (ชั้น 1): ข้อยกเว้นราย (def × grade) — **สูตรคือค่าเริ่มต้น override คือเจตนา**
ทั้งเซ็ตควรอ่านจบในหน้าจอเดียว เทสบังคับว่าแต่ละแถวต้อง (ก) ต่างจากสูตรจริง (ข) ไม่ห่างเกิน 2× เว้นแต่
ติด `deliberate` (ค) มี `why` — และมันถูก stamp ผ่าน `Item::assign_grade` ที่เดียว (ดรอป/ผสม/migrate)

**ลูปการจูน**: `cp data/game_data.json /tmp/t.json` → แก้ → `sim-cli --gear-report --data /tmp/t.json`
(ไม่ rebuild) → แก้ของจริง → `cargo test -p sim-core --lib` (บอก digest ใหม่) → `--tests` + bless →
`cp` ไป StreamingAssets (เทสจับถ้าลืม) → `tools/deploy.sh` (ไม่ deploy = version gate ปฏิเสธเซฟ online)

## 7.8 รูรั่ว fusion client-rolled — ปิดแล้วฝั่ง sim + server (0.0.377, 2026-09-15) · เหลือ client ต่อสาย

client รู้ seed ⇒ client ที่ถูกแก้ทำนาย 3 draw ถัดไปได้ ⇒ กดผสมเฉพาะจังหวะที่ได้ tier/ชนิด/สำเร็จที่ต้องการ
(peek-and-select ตัวเดียวกับที่ทำให้ refine ต้องย้ายไป server-roll) replay ยังผ่านเพราะไม่ผิดกฎสิม
ผลเสียหลัก: คนโกงได้ชนิดที่ต้องการทุกครั้ง = อุปสงค์ตลาดหาย (เหตุผลเดียวที่ output ต้องสุ่ม)

**การส่ง seed เป็นชุดล่วงหน้าไม่พอ** — เผา seed ที่ไม่ชอบด้วย Common 6 ชิ้นได้ · เลือก input ให้ tier ตกในช่องที่ seed ให้ชนิดที่ต้องการได้

### ที่ทำแล้ว (แบบพิมพ์เขียว = refine-roll 2b ที่ลบไปใน 0.0.370)

| ชั้น | กลไก |
|---|---|
| sim | `FuseGear { picks, server_roll }` (default 0 — log เก่าไม่เปลี่ยน) · `server_roll ≠ 0` อ่านผลทั้ง 3 (เหรียญ tier / สำเร็จ / ชนิด) ออกจาก nonce แบบ mixed radix **ไม่จับ draw เลย** · `0` = client-roll 3 draw เหมือนเดิม — จำนวน draw ขึ้นกับ *event* ที่อยู่ใน log ไม่ใช่ผล ⇒ replay ตรงทั้งสองทาง |
| เส้นแบ่ง | `fusion::FUSE_SERVER_ROLL_FROM = Legendary` — ผลลัพธ์ ≥ Legendary (คือ input ≥ Rare) ต้องมี nonce · ต่ำกว่านั้น client-roll ต่อ · sim รับทั้งสองทางทุก grade (total) — **verifier** เป็นคนปฏิเสธ 0 จากเส้นนี้ขึ้นไป (`FuseVerdict::HighNoRoll`) |
| binding | `fusion::binding(state, picks)` = product_key ทั้ง 6 **เรียงแล้ว** (ลำดับกดไม่มีผล) + `measures.fusions` (ตัวนับครั้ง ขยับทั้งสำเร็จ/fail) — ผูก *product* ไม่ใช่ instance เพราะผลไม่ขึ้นกับอย่างอื่นของ input ⇒ nonce ของชุด 6 ชิ้น product เดียวกันใช้แทนกันได้ **ถูกต้อง** |
| server | `POST /fuse/roll {key, attempt}` → nonce blake3(secret, account, key, attempt) 63-bit ไม่เป็น 0 · idempotent (ขอซ้ำได้ค่าเดิม = re-roll ด้วยการยกเลิกไม่ได้) · session tainted ถูกปฏิเสธ · ตาราง `fuse_outstanding` / `fuse_consumed` (รอด scale-to-zero) · orphan TTL 1 ชม. |
| verify ตอน save | (1) `verify_fuse_bindings` replay log ทั้งก้อน (ข้ามถ้าไม่มี FuseGear เลย) ก่อนถึงแต่ละ fusion คำนวณ binding จาก state จริงแล้วเทียบ nonce → target-selection / re-roll / nonce คนอื่น / 0 บนของสูง = reject + flag `fuse-bind-fail` · (2) `reconcile_fuse` เทียบเซ็ต nonce: ใช้แต่ไม่เคยออก = forgery reject + flag `forged-fuse-nonce` · ออกแต่ไม่ใช้ = **peek-and-skip suspect** ค้างใน `fuse_outstanding` ให้ชั้น audit |

**ที่ยังโกงได้ (เหมือน refine เดิม — รับรู้แล้ว)**: ขอ nonce ของหลายชุด (key ต่างกัน) ที่ attempt เดียวกัน แล้วเลือกกดชุดที่ผลดี — ทำได้ แต่ทุก nonce ที่ไม่ได้ใช้ค้างเป็น unconsumed ⇒ ตรวจจับได้ที่ audit ไม่ใช่ที่ reject · เป็นราคาที่ยอมรับเพื่อไม่ต้องล็อกกระเป๋าทั้งใบไว้กับ server ก่อนกด

### ที่เหลือ = client
- Unity ยังไม่มีหน้า Fusion — ตอนทำ: ก่อนกด ถ้า `fusion::needs_server_roll(grade)` ให้ `POST /fuse/roll` ด้วย `fusion::binding` แล้วส่ง `FuseGear { picks, server_roll: nonce }` · ถ้า server ปฏิเสธ (tainted/offline) **ไม่กด** (ห้าม fallback เป็น 0 — verifier จะ reject save)
- sim-host ยังไม่ expose `binding`/`needs_server_roll` เป็น JSON — เพิ่มพร้อมหน้า Fusion

## 7.5 FUTURE IDEA — Set item ที่ "ทำขึ้น" ไม่ใช่ "ดรอป"

> user 2026-09-14: "คิดว่าจะเพิ่มระบบ set item ในอนาคต → แต่การทำต้องใช้ไอเทม original มา enchant
> เพื่อเพิ่ม set effect ลงไป **เป็นแค่ไอเดียก่อน**" — บันทึกไว้ ยังไม่ออกแบบ

**มันเข้ากับโครงนี้พอดีโดยไม่ต้องต่อเติมอะไร** และนั่นคือเหตุผลที่ควรจดไว้ตรงนี้:

- set effect ที่ **เกิดจากการ enchant ของ base** = รูปเดียวกับ ★/line ทุกประการ — ของดิบยัง fungible
  และขายได้, ความลึกยังอยู่หลังการลงมือของผู้เล่น, ชิ้นที่ทำแล้ว bound ⇒ **ไม่มีกฎใหม่ในระบบตลาด**
- ไม่ต้องมี "ชิ้น set" ในตารางดรอป ไม่ต้องมี item class ใหม่ — set เป็น *ผลลัพธ์ของ enchant*
- มันให้เหตุผลกับ enchant ที่ตอนนี้ยังไม่มี: วันนี้ enchant = "stat เยอะขึ้น" (เชิงปริมาณ)
  ถ้ามี set มันจะกลายเป็น "จะผูกชิ้นไหนเข้าชุดเดียวกัน" = **การตัดสินใจเชิง build** ซึ่งตรงกับเสาหลัก
  "build อยู่ที่ระดับการจัดปาร์ตี้/ของ" ไม่ใช่ที่ตัวเลข
- และมันให้ปลายทางกับการผสม: ต้องมีของ tier สูงหลายชิ้นก่อนจะผูกเป็นชุดได้ → อุปสงค์ของชิ้นที่ผสมมา

**สิ่งที่ต้องคิดตอนจะทำจริง** (จดไว้ให้ไม่ต้องค้นใหม่):
1. set effect คือ **bonus ที่มีเงื่อนไข** (ใส่ครบ N ชิ้นของชุดนั้น) — pipeline ของเราสรุป mod เป็น
   bucket แล้วคูณครั้งเดียว (`combat::stat_mods`, `gear_mods` 26 hook) ⇒ ต้องเพิ่ม **ชนิดเงื่อนไข**
   ("นับชิ้นที่มี set id X แล้วใช้ชั้นที่ N") ไม่ใช่เพิ่ม stat ใหม่
2. เก็บ `set_id` ไว้บน **instance** (ผลของ enchant) + ตารางเอฟเฟกต์ต่อชุดใน catalog
3. **แก้ไม่ได้ = ความเสี่ยงของผู้เล่น**: enchant แล้ว bound ถาวร ⇒ ผูกชุดผิดคือเสียของ
   TBH มี Extraction ไว้ตรงนี้ (จ่าย gold ถอดออก, crystal หาย) — ต้องตัดสินว่าเรามีทางถอน/เปลี่ยนชุดไหม
4. set ต้อง **หาได้ด้วยการเล่น** ไม่ใช่ของกาชาเท่านั้น (ตาม positioning: free-via-market ต้องเป็นไปได้)

## 8. ทำไมโครงนี้ชนะของเดิม (สรุปเชิงเหตุผล)

1. **ผู้เล่นไม่ต้องตัดสินใจต่อชิ้น** — ของบอกเองว่าไปไหน (ดรอป→ผสม, tier สูง→เลือกได้จริง)
2. **กระเป๋าไม่เต็ม** — base เป็น count + auto-combine ⇒ ไม่ต้องมี auto-sell threshold,
   ไม่ต้องเขียน script ภายนอกแบบที่ผู้เล่น TBH ต้องทำ (และ TBH **ขาย Stash Pack เป็น DLC**)
3. **ของทุกชิ้นมีที่ใช้** — รวมอาวุธ 88 ชิ้นที่ไม่มีตัวละครใส่ (ถ้า D6 ผ่าน มันคือวัตถุดิบ)
4. **ตลาดทำงานได้จริง** — fungible = มี order book, ตั้งราคาได้, ไม่เป็น lemon market
5. **ความลึกไม่หาย** มันย้ายไปอยู่ที่ enchant ซึ่งผู้เล่น**เลือกเข้าไปเสี่ยงเอง**
6. **เรามีสิ่งที่ TBH ไม่มี**: replay-verify → ของที่โกงมาไม่มีทางเกิด ไม่ต้องแบนย้อนหลัง/รีเซ็ตของ
   ทั้งเซิร์ฟแบบที่เขาต้องทำในเดือน มิ.ย. 2026
