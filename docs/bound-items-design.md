# ของที่ไม่อยู่ในกระเป๋า — ตั๋วกาชา ตั๋ว EXP ไอเทม cash

ร่างสถาปัตยกรรม 2026-08-18 · **คำถามท้ายไฟล์ตอบครบแล้ว (user 2026-08-18)** ดูหัวข้อ "ที่ตัดสินแล้ว"
ยังไม่ลงมือ

## โจทย์

ของบางอย่างต้องไม่กินช่อง `inventory` และต้องไม่หายเพราะกระเป๋าเต็ม — ตั๋วกาชา ตั๋ว EXP
ไอเทมที่ซื้อด้วยเงินจริง

## สิ่งที่มีอยู่แล้ว — สามบ้าน อย่างละหนึ่ง

**อย่าสร้างบ้านที่สี่ก่อนพิสูจน์ว่าสามหลังนี้ไม่พอ**

| บ้าน | ที่อยู่ | รูปทรง | ตัวอย่างที่ใช้อยู่ |
|---|---|---|---|
| **สิมรู้จัก** | `GameState.owned_exemplars` / `owned_regalia` | `Vec<Item>` ไม่จำกัดจำนวน ไม่เข้า inventory/stash/market | Exemplar, Regalia |
| **เซิร์ฟเวอร์รู้จักคนเดียว** | `crystal_wallet` + `crystal_ledger` | ตัวนับ แยก tradeable/bound มี ledger | เจม |
| **สิทธิ์ถาวร** | `entitlements` | หนึ่งแถวต่อการซื้อ มี `sku` / `order_id` / `revoked_at` | ของที่ซื้อด้วยเงินจริง |

`owned_exemplars` (0.0.220) มีคอมเมนต์เขียนเหตุผลไว้ตรงตัว: *"separate from `inventory` so a
precious Exemplar can never overflow-drop"* — คือโจทย์เดียวกับที่ตั้งไว้ข้างบนเป๊ะ และทั้งคู่ใช้
`#[serde(default, skip_serializing_if = "Vec::is_empty")]` ซึ่งทำให้เซฟเก่ากับ golden hash
เหมือนเดิมทุกไบต์ตอนเพิ่มช่อง — เทคนิคนี้ต้องเอามาใช้ต่อไม่ว่าจะเลือกทางไหน

## กฎที่ตัดสินว่าของชิ้นหนึ่งอยู่บ้านไหน

คำถามไม่ใช่ "เก็บที่ไหนดี" แต่คือ **ใครต้องพิสูจน์มันได้**

> **ของชิ้นนี้มีส่วนร่วมในการจำลอง *ระหว่างที่ถืออยู่* หรือไม่**

- **มี** → ต้องอยู่ใน `GameState` เพราะ replay ต้องได้ผลเท่ากันทุกครั้ง · Exemplar ถูก **สวม**
  แล้วเปลี่ยนค่าสถานะและผลการต่อสู้ ตัวไอเทมจึงร่วมอยู่ในสมการ
- **ไม่มี** → อยู่ฝั่งเซิร์ฟเวอร์ · ตั๋วถูกถือไว้เฉย ๆ แล้ววันหนึ่งถูกใช้ ระหว่างที่ถือมันไม่
  เปลี่ยนอะไรในสิมเลย

กฎนี้ไม่ได้คิดขึ้นใหม่ — มันคือเหตุผลที่ `owned_exemplars` อยู่ในสิมแต่ `crystal_wallet` ไม่อยู่

## เอากฎมาใช้กับของสามอย่าง

| | ร่วมในการจำลองตอนถือ? | บ้าน | เหตุผล |
|---|---|---|---|
| **ตั๋วกาชา** | ไม่ | `crystal_wallet` แบบเดียวกัน (ตัวนับฝั่งเซิร์ฟเวอร์) | การโรลเกิดฝั่งเซิร์ฟเวอร์อยู่แล้ว สิมไม่เคยเห็นทั้งตั๋วและผล |
| **ตั๋ว EXP** | ไม่ | ตัวนับฝั่งเซิร์ฟเวอร์ + grant | ดูหัวข้อถัดไป — นี่คือข้อที่คนมักตัดสินผิด |
| **ไอเทม cash ถาวร** | ไม่ (มันคือ*ความสามารถ* ไม่ใช่*จำนวน*) | `entitlements` | มี `sku`/`order_id`/`revoked_at` ให้แล้ว เช่น +3 ช่อง rare bag |

### ทำไมตั๋ว EXP ถึงไม่ควรอยู่ในสิม ทั้งที่ผลของมันอยู่ในสิม

ดูเผิน ๆ ตั๋ว EXP ต้องอยู่ในสิม เพราะใช้แล้ว EXP เพิ่ม ซึ่งเป็นสถานะที่ replay ต้องสร้างซ้ำได้
แต่ต้องแยกระหว่าง **ตั๋ว** กับ **ผลของตั๋ว**

- ถ้าตั๋วอยู่ในสิม: เซิร์ฟเวอร์ต้อง grant ตั๋วเข้า `GameState` → client เขียน input "ใช้ตั๋ว" →
  สิมเพิ่ม EXP → เซิร์ฟเวอร์ replay แล้วต้องตรวจว่าตั๋วมีจริง **สองต่อ และ client ถือสำเนาจำนวนตั๋ว**
- ถ้าตั๋วอยู่ฝั่งเซิร์ฟเวอร์: client ขอ "ใช้ตั๋วหนึ่งใบ" → เซิร์ฟเวอร์ลดจำนวนแล้วออก **grant** →
  grant เข้าสิมผ่านทางที่มีอยู่แล้ว (ทางเดียวกับ mail claim และ drop grant) **ต่อเดียว และจำนวน
  ตั๋วไม่เคยอยู่ในมือ client**

ทางที่สองถูกกว่าและปลอดภัยกว่า และไม่ได้เป็นการคิดกลไกใหม่ — `mailbox_grant.rs` ทำแบบนี้อยู่แล้ว

**ข้อแลกเปลี่ยนที่ต้องยอมรับ:** ใช้ตั๋วต้องออนไลน์ ซึ่งไม่ใช่ข้อจำกัดใหม่ ([[no-offline-version]])

## ที่เสนอ

**ตัวตั๋วไม่แตะ sim-core เลย** ไม่มีช่องใหม่ใน `GameState` ไม่มี `ItemKind` ใหม่ goldens ไม่ขยับ
save schema ไม่เปลี่ยน replay ไม่มีความเสี่ยงใหม่

> ⚠️ **แก้ 2026-08-18** — ประโยคนี้เคยเขียนว่า "ไม่แตะ sim-core เลย" ซึ่งไม่จริงอีกต่อไปหลังตอบข้อ 2
> ว่าเอาตั๋ว EXP **ทั้งสองแบบ** ตัวตั๋วยังอยู่นอกสิมทั้งคู่ แต่ *ผล* แบบคูณตามเวลาต้องเข้าสิม
> ดูหัวข้อ "ที่ตัดสินแล้ว"

```sql
-- แถว ไม่ใช่คอลัมน์: ของชนิดใหม่ = ข้อมูล ไม่ใช่ migration
CREATE TABLE bound_items (
    account_id  BIGINT NOT NULL,
    kind        TEXT   NOT NULL,   -- 'ticket_gacha' | 'ticket_exp_s' | …
    qty         BIGINT NOT NULL DEFAULT 0,
    PRIMARY KEY (account_id, kind)
);
```

`entitlements` ยังใช้กับของถาวร (สิทธิ์) `bound_items` ใช้กับของที่นับจำนวนและใช้แล้วหมด
เหตุผลที่ไม่ยัดรวม: การเพิกถอนคนละความหมาย — สิทธิ์ถูก `revoked_at` ได้เมื่อขอคืนเงิน
ส่วนตั๋วที่ใช้ไปแล้วเรียกคืนไม่ได้

**ต้องมี ledger เหมือน `crystal_ledger`** ตั๋วที่ซื้อด้วยเงินจริงคือของที่ต้องตอบได้ว่าหายไปไหน
ตัวนับที่แก้ได้และ drift เงียบได้คือสิ่งที่ `docs/economy-invariants.md` I7 มีไว้กัน

## ทำไมไม่เลือกทางที่ดูสมมาตรกว่า

**"ยุบ `owned_exemplars` + `owned_regalia` + ตั๋ว เป็น `bound_items: Vec<Item>` อันเดียวในสิม"**
สวยกว่าบน schema แต่ต้องย้ายของผู้เล่นจริงสองกอง = golden hash ขยับ + migration บนเซฟจริง
แลกกับความสวย ไม่คุ้ม และตั๋วไม่ควรอยู่ในสิมตั้งแต่แรกตามกฎข้างบน

**"ทำ Vec ที่สามในสิม (`owned_tickets`)"** ตามรอยที่ทำมาแล้วสองครั้ง migrate ง่าย แต่แพงกว่า
ทางที่เสนอโดยไม่ได้อะไรกลับมา — และทำให้ client ถือสำเนาจำนวนตั๋วโดยไม่จำเป็น

|---|---|---|

### ตั๋ว EXP สองแบบ — เส้นแบ่งอยู่ที่ *ผล* ไม่ใช่ *ตั๋ว*

กฎในหัวข้อข้างบนยังใช้ได้ทั้งดุ้น และมันตอบสองครั้งด้วยคำตอบต่างกัน เพราะคำถามคือ
**"ระหว่างที่ถืออยู่ ของชิ้นนี้ร่วมในการจำลองไหม"** — ตั๋วที่ยังไม่ใช้ไม่ร่วมทั้งคู่

| | ตั๋วอยู่ไหน | ผลอยู่ไหน |
|---|---|---|
| **ให้ EXP ก้อนเดียวทันที** | `bound_items` | grant ครั้งเดียว จบในจังหวะนั้น |
| **คูณ EXP ตามเวลา** | `bound_items` เหมือนกัน | **ต้องอยู่ใน `GameState`** — ทุก EXP ที่เข้าระหว่าง buff เปิด ต้อง replay ได้เท่าเดิม |

**สิ่งที่ต้องเพิ่มในสิม มีแค่ฝั่งผล ไม่ใช่ฝั่งตั๋ว**

- ช่องใหม่ใน `GameState` เก็บตัวคูณกับ**จำนวน tick ที่เหลือ** ห้ามเป็นเวลาจริง สิมไม่มีนาฬิกา
  และ replay ต้องได้ผลเท่ากันทุกครั้ง · 2 ชั่วโมง = 72,000 tick (10 tick/วินาที)
- `#[serde(default, skip_serializing_if)]` แบบเดียวกับ `owned_exemplars` เซฟเก่าและ golden hash
  จึงเหมือนเดิมทุกไบต์ตอนเพิ่มช่อง
- `InputEvent` ตัวใหม่ที่เป็น `InputAuthority::Server` — ตระกูลเดียวกับ `GrantDrop` / `GrantCraft`
  / `GrantGear` / `ClaimMail` ที่มีอยู่แล้ว ⚠️ ตัวใหม่ในตระกูลนี้ **ไม่มีใครตรวจจนกว่าจะเขียน
  verdict ให้** — `every_server_authored_event_has_a_verdict` จะทำให้ build แดงจนกว่าจะเขียน
- นับถอยหลังใน `tick()` และเอาตัวคูณไปคูณตรงจุดที่ EXP เข้า

**ยังไม่มี grant EXP ในสิมเลย** ตรวจแล้ว ตระกูล `Grant*` ทั้งหมดส่งไอเทมกับ Gil ไม่มีตัวไหนส่ง EXP
แปลว่าตั๋วแบบ "ก้อนเดียวทันที" ก็ต้องมี `InputEvent` ใหม่เหมือนกัน — ประโยค "ไม่แตะ sim-core เลย"
ในหัวข้อ "ที่เสนอ" จึงเป็นจริงเฉพาะกับตั๋วกาชา

### ตั๋วกาชากลายเป็นเงินที่ใช้จั่ว (user 2026-08-18)

ตอนนี้ `gacha_roll` เรียก `gacha::cost_of(count)` แล้วหักเจมตรง ๆ ที่ขอคือแทรกชั้นตั๋วเข้ามาแบบเกม
กาชาทั่วไป: **เจม → ซื้อตั๋ว → จั่วด้วยตั๋ว** กด 10 จั่วต้องมีตั๋วครบ 10 ก่อน

นี่คือส่วนที่ทำให้ `bound_items` **มีคนใช้ตั้งแต่วันแรก** แทนที่จะเป็นระบบที่สร้างเสร็จแล้วต่อกับ
ของที่ยังไม่ ship ([[systems-built-but-unreachable]] เกิดซ้ำในโปรเจกต์นี้มาแล้ว)

**บันไดล็อกอิน 7 วันแรกจ่ายเป็นตั๋วกาชา (user 2026-08-18):** `1 1 2 1 1 1 3` = **10 ใบพอดี**
สัปดาห์แรกของบัญชีใหม่จึงจบที่การจั่ว 10 ครั้งฟรีหนึ่งรอบ ไม่ใช่เศษที่ค้างอยู่

⚠️ **นี่คือลำดับที่ต้องระวัง** — `schedule.rs` มี `Grant` แค่ `Crystal` / `Gil` / `Item` ตั๋วต้องเป็น
variant ที่สี่ที่เขียนลง `bound_items` ดังนั้น **บันไดนี้จ่ายตั๋วไม่ได้จนกว่า `bound_items` จะมีจริง**
ตอนนี้ `login7()` จ่ายเจมกับเกราะไว้ชั่วคราว ต้องเปลี่ยนทั้งแถวเมื่อตั๋วพร้อม

ที่ต้องคิดต่อ ยังไม่ตัดสิน

- กดจั่ว 10 แล้วตั๋วไม่ครบ — ซื้อส่วนที่ขาดให้อัตโนมัติในกดเดียว หรือเด้งไปหน้าซื้อ
- `idem_key` ตอนนี้คุมทั้งการจั่ว ถ้าแยกเป็นสองก้าว (ซื้อ / จั่ว) **ต้องคุมทั้งสองก้าว** ไม่งั้น
  จังหวะที่หักเจมแล้วแต่จั่วไม่สำเร็จจะกลายเป็นตั๋วที่หายไป
- ราคาต่อตั๋วต้องเท่ากับ `cost_of(1)` เป๊ะ ไม่งั้นการแทรกชั้นนี้คือการขึ้นหรือลดราคาเงียบ ๆ

## คำถามที่ตอบไปแล้ว (เก็บไว้เพราะเหตุผลคือสาระ)

1. **ตั๋วซื้อขายในตลาดได้ไหม** — ถ้าได้ ต้องแยก tradeable/bound แบบ `crystal_wallet` และตั๋วต้อง
   เข้าตลาดได้ ซึ่งเป็นงานคนละก้อน · ถ้า bound ตลอด ตัดออกได้ทั้งหมด
2. **ตั๋ว EXP ให้ EXP ทันที หรือเป็น buff คูณต่อเนื่อง** — "ทันที" คือ grant ก้อนเดียว ตรงตามที่
   เสนอ · "คูณ 2 ชั่วโมง" **ต้องอยู่ในสิม** เพราะ replay ต้องรู้ว่าตอนนั้น buff เปิดอยู่ ซึ่งพลิก
   คำตอบทั้งหมดสำหรับตั๋วชนิดนั้น
3. **หายตอน wipe ไหม** — `soul` รอด `stash` ไม่รอด ตั๋วที่จ่ายเงินซื้อควรรอด แล้วตั๋วที่ได้ในเกม?
4. **จำนวนชนิดที่คาดไว้** — 3-5 หรือหลายสิบ (ตอบแล้วยืนยันว่าเลือกแถวถูกแล้ว)
5. **ของที่ได้มาระหว่างเซิร์ฟเวอร์ล่ม** — ตอนนี้ mail คือทางส่งของ ตั๋วควรมาทาง mail แล้วค่อย
   ตกลง `bound_items` หรือเข้าตรง ๆ
