# ช่อง Party Buff — บัฟชั้นที่สองเหนือของกินส่วนตัว

ตัดสิน 2026-08-18 (user) · **ยังไม่ลงมือ**

## โจทย์

`ProvisionsView` วันนี้เป็นของ**ต่อตัว** — แถวคือสมาชิก คอลัมน์คือ 3 ช่องฉุกเฉิน + 2 ช่องจอง
(Meal / Tonic) เพิ่ม **ช่องระดับปาร์ตี้ 3 ช่อง** ที่บัฟทุกคนพร้อมกัน

## ข้อค้านที่มีอยู่แล้วในโค้ด และทำไมมันไม่เกี่ยว

`provisions_view.gd` เขียนค้านไว้ตรงตัวว่าอย่าไปทางนี้

> friction that pushes the design toward one item buffing the whole party, **which would quietly
> cut the craft sink by 80%**. This is what makes per-character consumption bearable, and
> per-character consumption is the sink.

ข้อค้านนั้นกลัวการ **แทนที่** — ของชิ้นเดียวมาแทนของห้าชิ้น แต่สิ่งที่ทำคือ **สองชั้นซ้อนกัน**
(user): ช่องส่วนตัวอยู่ครบเหมือนเดิมและถูกกินเท่าเดิม ช่องปาร์ตี้เป็น stream ใหม่ที่เพิ่มมา
sink จึงโตขึ้น ไม่ได้หด — ข้อค้านนั้นไม่ตรงกับสิ่งนี้ และไม่ต้องแก้ตัวเลขอะไรเลย

## กลไกที่มีอยู่แล้ว ไม่ต้องประดิษฐ์

`apply_buff` แทนที่ buff เมื่อ **`(kind, source_id)` ตรงกันทั้งคู่** — คนละ `source_id` จึงซ้อนกัน
เป็นคนละก้อน และโค้ดสงวน `source_id` ไว้สี่ตัวแล้วด้วยเหตุผลนี้เอง

    AURA_SOURCE             party aura, ล้าง+ปั๊มใหม่ทุก tick
    PATH_AURA_SOURCE        Paths of Soul
    GOD_BUFF_SOURCE
    CONSUMABLE_BUFF_SOURCE  ← ของกินส่วนตัวใช้ตัวนี้

ชั้นปาร์ตี้จึงซ้อนกับชั้นส่วนตัวได้โดย **ไม่ต้องแตะ `apply_buff` และไม่ต้องแก้กฎการซ้อน**

## ที่ตัดสินแล้ว

| | |
|---|---|
| จำนวนช่อง | **3 ระดับปาร์ตี้ ไม่จำกัดชนิด** — ทรงเดียวกับช่องฉุกเฉิน ไม่ใช่ทรงช่องจอง จึงไม่ต้องมี `ProvisionKind` variant ใหม่ แค่ธงว่าของชิ้นนี้ลงช่องปาร์ตี้ได้ |
| บัฟอะไรได้ | อะไรก็ได้ |
| **ห้ามใส่ของชิ้นเดียวกันซ้ำช่อง** | กฎเดียวที่มี และเป็นตัวที่ทำให้ 3 ช่องเป็นการเลือกจริง แทนที่จะเป็น "ใส่ของดีที่สุดสามอัน" |
| ที่มา | **cash shop เป็นหลัก** + ได้จาก event ล็อกอิน ฯลฯ |
| การเติม | `BuffMissing` เหมือนของส่วนตัว กินทีละ 1 ต่อการรีเฟรช |
| ใครได้ | สมาชิกที่ยังไม่ตายทุกคน |

### ⚠️ สาม `source_id` ไม่ใช่หนึ่ง — เป็นข้อกำหนด ไม่ใช่ข้อควรระวัง

**+ATK สามช่องจากของคนละชิ้น ต้องได้ครบสาม (user 2026-08-18)** กฎห้ามซ้ำคุมแค่ *ชื่อของ* ไม่ได้
คุมชนิดของ buff ดังนั้นสามชิ้นที่เพิ่ม ATK เหมือนกันคือการตั้งค่าที่ถูกต้องและต้องทำงาน

`apply_buff` แทนที่เมื่อ `(kind, source_id)` ตรงกัน — ถ้าทั้งสามช่องใช้ `source_id` ตัวเดียว
การตั้งค่านั้นจะ **ยุบเหลือ buff เดียว** ผู้เล่นเต็มสามช่อง จ่ายของสามชิ้น และได้ผลชิ้นเดียว
โดยไม่มีอะไรบอก จึงต้องสงวน `source_id` แยกช่องละตัว

**เขียนเทสตรงเคสนี้** — ของสามชิ้นที่ให้ BuffKind เดียวกัน ต้องปรากฏเป็น buff สามก้อนและค่ารวม
ต้องเท่ากับผลบวก เทสที่ใส่ของสามชนิดต่างกันจะผ่านทั้งที่โค้ดผิด

## ของชิ้นนี้อยู่ใน `GameState` ไม่ใช่ `bound_items`

กฎใน `docs/bound-items-design.md` เป็นคนตัดสิน — *"ระหว่างที่ถืออยู่ ของชิ้นนี้ร่วมในการจำลองไหม"*

ตั๋วกาชานอนเฉย ๆ จนถูกใช้ → ไม่ร่วม → อยู่ฝั่งเซิร์ฟเวอร์ · **ของที่นั่งอยู่ในช่องแล้วเติม buff
ทุกครั้งที่หมด ร่วมอยู่ตลอดเวลา** → ต้องอยู่ในสิม เพราะ replay ต้องได้ค่าความเสียหายเท่าเดิม

**ไม่ต้องสร้างทางส่งใหม่** — cash shop → mail → กระเป๋า → ลากลงช่อง เป็นเส้นเดิมทุกช่วง เส้นเดียว
กับ Exemplar ที่ซื้อด้วยเงินจริงแล้วเข้าสิม

## สิ่งที่ต้องเพิ่ม

| | |
|---|---|
| ฟิลด์ใหม่ฝั่ง party-shared ใน `GameState` | คู่กับ `stash`/`gil`/`soul` + `#[serde(default, skip_serializing_if)]` → golden ไม่ขยับ เซฟเก่าเหมือนเดิมทุกไบต์ (เทคนิคเดียวกับ `owned_exemplars`) |
| `source_id` สงวนสามตัว | ดูข้างบน |
| `InputEvent` วาง/ถอนของในช่องปาร์ตี้ | ทรงเดียวกับตัวที่ย้าย provision อยู่แล้ว · input ที่ไม่ถูกต้องต้องเป็น no-op เงียบ ห้าม panic (replay ต้องรอด version skew) |
| กฎห้ามซ้ำ **บังคับในสิม** | UI ทำให้กดไม่ได้ก็ดี แต่สิมคือผู้ตัดสิน |
| `ProvisionsView` เพิ่ม **แถว** เหนือ grid | ไม่ใช่คอลัมน์ — มันไม่ใช่ของต่อตัว |

## ที่ยังไม่ตัดสิน

**ขายในตลาดได้ไหม** — ถามแล้วยังไม่ได้คำตอบ สมมติไว้ว่า **ยังไม่ให้ขาย** และเดินต่อได้ เพราะ
เปิดให้ขายทีหลังทำได้ ส่วนปิดทีหลังทำไม่ได้

`monetization-positioning` บอกว่าสิ่งที่ทำให้ pay-for-power ป้องกันได้คือ *หาได้ฟรีด้วย + PvE
ผ่านได้โดยไม่ซื้อ + PvP จับคู่กัน* — ขาแรกมีแล้วจาก event ล็อกอิน จึงไม่ต้องพึ่งตลาดเพื่อให้ยืนได้

**และต้องเรียกมันว่า pay-for-power ตรง ๆ ในเอกสารภายใน ไม่ใช่ cosmetic** — มันมีค่าสถานะ
