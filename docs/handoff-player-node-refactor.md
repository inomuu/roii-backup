# Handoff — ทำสมาชิกปาร์ตี้ให้เป็นโหนด (รีแฟกเตอร์ `views/`, เกม 2D)

เขียน 2026-08-13 · งานนี้เป็นการรีแฟกเตอร์ **เกม 2D ปัจจุบัน**

> ⚠️ **แก้ 2026-08-18** — ตอนเขียน งานสามมิติยังเป็นต้นแบบที่ทิ้งได้ **ตอนนี้ไม่ใช่แล้ว**
> HD-2D ถูกรับเป็นทิศทางเมื่อ 16 ส.ค. และ `proto/arena3d/main3d.tscn` บูตเข้าหน้า login
> กับหน้าสร้างตัวละครตัวจริงเหมือนไคลเอนต์ 2D ทุกประการแล้ว (`tools/play.sh --3d`)
> คำว่า "ไม่ต้องแตะ" ในเอกสารนี้แปลว่า **งานรีแฟกเตอร์ชิ้นนี้ไม่ต้องไปยุ่ง** เพื่อให้ขอบเขต
> ของมันแคบ — ไม่ได้แปลว่าห้ามใครแตะสามมิติ ถ้ากำลังทำเรื่องอื่นอยู่ แตะได้ตามปกติ

## 1. เป้าหมาย

**ทำให้สมาชิกปาร์ตี้เรนเดอร์ด้วยโหนดของตัวเอง แบบเดียวกับที่มอนสเตอร์ทำอยู่แล้ว**

ตอนนี้โค้ดเบสมีสองแบบแผนอยู่พร้อมกัน:

| | มอนสเตอร์ | ผู้เล่น |
|---|---|---|
| ตัวเรนเดอร์ | `views/base_monster.gd` — `Node2D` + `AnimatedSprite2D` | `views/player_animator.gd` — `RefCounted` |
| การวาด | โหนดวาดตัวเอง | `draw_player()` วาดแบบ immediate mode |
| โหนดต่อตัว | `BaseMonster` เต็มตัว | `Node2D` เปล่าที่ callback กลับเข้า animator |

ผู้เล่นมีโหนดอยู่แล้ว (`sync_players` สร้าง `Node2D` ต่อคน) แต่มันเป็นแค่เปลือกสำหรับจัดลำดับ
หน้าหลัง — ตรรกะและการวาดจริงยังอยู่ใน `player_animator.gd` ทั้งหมด

## 2. ทำไมถึงคุ้ม (เกม 2D ได้ประโยชน์ทันที ไม่ต้องรอเรื่องสามมิติ)

- **แบบแผนเดียวทั้งโค้ดเบส** — คนอ่านโค้ดไม่ต้องเรียนสองระบบ
- **ตัดการผูกกับ `arena`** — `player_animator.gd` เรียกใช้สมาชิกของ `arena` อยู่ **14 ตัว**
  (`state` ×5 · `skin_textures` ×2 · `sim_driver` ×2 · `glide` ×2 · `cell_px` ×2 ·
  `_display_pos` ×2 · `TICK_INTERVAL` · `tick_acc` · `origin` · `create_tween` ·
  `_texture_for_class` · `_is_gliding` · `_anim_alive`) ซึ่งทำให้แยกทดสอบหรือย้ายที่ไม่ได้เลย
  `BaseMonster` รับ state เข้ามาทาง `apply()` ครั้งเดียวและไม่รู้จัก arena
- **`arena_draw.gd` ผอมลง** — เป้าหมายระยะยาวคือลดการวาดแบบ immediate mode
  (ตอนนี้ 862 บรรทัด 72 จุดวาด) ตามแนวทาง UI ที่ตัดสินไว้แล้วเมื่อ 2026-07-08
- **ผลพลอยได้:** ถ้าวันหนึ่งตัดสินใจทำ HD-2D การพอร์ตจะกลายเป็นการคัดลอกมาแก้ไม่กี่จุด
  เหมือนที่ `BaseMonster` ทำได้ แทนที่จะต้องสร้าง shim มาหลอก 14 สมาชิก

## 3. กฎเหล็ก

1. **คัดลอกและย้าย ห้ามเขียนใหม่** — `player_animator.gd` 951 บรรทัดคือการจูนสะสมหลายปี
   ที่หน้าตาเหมือนโค้ดธรรมดา ต้องรักษาไว้ทุกอย่าง:
   - hitstop (`hitstop_frame`)
   - lunge tween ที่ **ล็อกทิศตอนเริ่มสวิง** (`strike_dir_x/y`) ไม่ใช่ทิศปัจจุบัน
   - `impact` / `lunge_from` / `strike_end` ต่อคลิป ที่ซิงก์กับจังหวะที่สิมคิดดาเมจ
   - hurt flash · Hiding (จาง) · Poison (ม่วงอมเขียว) · ออร่า Exemplar ที่เต้นตามเวลา
   - **การพลิกภาพผ่าน canvas transform** — คอมเมนต์ระบุว่าเคยใช้ source กว้างติดลบแล้ว
     **เกิดรอยต่อ 1 พิกเซล** ห้ามเปลี่ยนกลับ
   - `SHEET_GEOM` ต่อคลาส (`fw`/`fh`/`foot`/`lift`/`faces_left`) — เฟรมไม่เท่ากันทุกคลาส
     สวอร์ดแมนคือ 55×60 ส่วนคลาสอื่น 60×60
   - ระบบสกิน `SKINS` + `ANIM_SLOTS` + `REQUIRED_ANIMS` (สำหรับ Exemplar)
2. **พฤติกรรมต้องเหมือนเดิมเป๊ะ** งานนี้คือการย้ายที่อยู่ของโค้ด ไม่ใช่การปรับปรุง
   ถ้าเห็นอะไรที่อยากปรับ ให้จดไว้แยก อย่าปรับไปพร้อมกัน
3. **งานรีแฟกเตอร์ชิ้นนี้ไม่ต้องแตะ `godot/proto/`** — เพื่อคุมขอบเขต ไม่ใช่เพราะสามมิติเป็น
   เขตหวงห้าม (ดูกล่องเตือนบนหัวไฟล์) `main3d.gd` สืบทอดจาก `main.gd` ทั้งดุ้น ดังนั้นถ้า
   รีแฟกเตอร์นี้เปลี่ยนโครง `views/` สามมิติจะได้ตามไปเองเป็นส่วนใหญ่ ที่ต้องระวังคือ
   `main3d.tscn` เป็นไฟล์ฉากแยก — โหนดที่เพิ่มใน `main.tscn` ต้องเพิ่มที่นั่นด้วยมือ และ
   ไม่มีอะไรจับได้ถ้าลืม

## 4. รูปแบบเป้าหมาย — ดู `views/base_monster.gd` เป็นแม่แบบ

โครงที่ควรได้:

```
PlayerNode (Node2D)
  └── Sprite (AnimatedSprite2D)
```

API ที่ควรมี เลียนแบบ `BaseMonster`:

| ของ `BaseMonster` | ความหมาย |
|---|---|
| `static build_frames(tex, fw, fh, clips, fps) -> SpriteFrames` | สร้างคลิปครั้งเดียว แคชไว้ |
| `setup(sf, hit_frame, ...)` | ตั้งค่าครั้งเดียวตอนสร้าง |
| `apply(e, world_pos, gliding, target_x, target_pos)` | **รับ state เข้ามา ไม่ไปดึงจาก arena** |
| `signal hit_landed(attacker_id)` | ยิงตอนถึงเฟรมสัมผัส |
| `signal death_finished(entity_id)` | ให้ตัวจัดการเก็บโหนด |
| `_drive_anim(alive, want_attack, got_hit, gliding)` | เลือกคลิป: death > attack > hurt > move > idle |

`player_animator.gd` จะเหลือหน้าที่เป็น **ตัวจัดการ** (สร้าง/เก็บโหนด, แคช `SpriteFrames`,
เก็บตาราง `CLASS_ANIM`/`SHEET_GEOM`/`SKINS`) แบบเดียวกับที่ `enemy_animator.gd` เป็นให้ `BaseMonster`

## 5. จุดที่ต้องระวังเป็นพิเศษ

- **`draw_player()` คำนวณ `src` / `dest` / `modulate` / `facing_left` แล้วค่อยวาด**
  (ราวบรรทัด 818-893) การย้ายไปเป็นโหนดคือการให้ `AnimatedSprite2D` ถือ `src` แทน
  แต่ **`dest` มีทั้งการยึดเท้า (`foot`) และ `lift` อยู่ในนั้น** ต้องแปลงเป็น `offset`
  ของสไปรท์ให้ตรง ไม่งั้นตัวละครจะลอยหรือจม
- **ออร่า Exemplar เป็นการวาดวงกลม/ส่วนโค้งแยกจากตัวสไปรท์** และเช็ค
  `ArenaRenderData.FX_ENABLED` อยู่ — ต้องคงการเช็คนี้ไว้ (โหมดหน้าต่างมุมจอปิด FX)
- **`sync_players` จัดลำดับหน้าหลังโดยใช้ตำแหน่งเท้าเป็นคีย์** และ interleave กับโหนดมอนสเตอร์
  ในเลเยอร์เดียวกัน อย่าทำให้ลำดับเปลี่ยน
- **สัตว์เลี้ยง (`is_pet`) เรนเดอร์เป็น `BaseMonster` อยู่แล้ว** ไม่ใช่ผู้เล่น — ข้ามไว้เหมือนเดิม

## 6. การทดสอบ

**ไม่มีเทสต์ใดครอบคลุม `godot/` เลยสักไฟล์** (CLAUDE.md ระบุไว้ชัด) เพราะงั้นต้องเห็นด้วยตา:

- เปิดเกมจริง ดูให้ครบ: เดิน · โจมตีระยะประชิด (สังเกต lunge ว่าพุ่งสุดตรงเฟรมสัมผัส) ·
  โจมตีระยะไกล (ต้องไม่ lunge) · โดนตี (flash) · ตาย · ธีฟตอน Hiding · ตอนติดพิษ ·
  สมาชิกที่ใส่ Exemplar (ออร่า) · ทุกคลาสทั้ง 5 เพราะเฟรมและแถวไม่เท่ากัน
- **เทียบก่อน/หลังด้วยตา** ถ้ารู้สึกว่า "จังหวะเปลี่ยนไปนิดหน่อย" แปลว่ามีการจูนหลุดไป
- `cargo test` ไม่ช่วยอะไรกับงานนี้ สิมไม่ถูกแตะ
